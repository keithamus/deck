Deck

A simple slide deck with Web Components

This is a deck in a single HTML file. Press S for the presenter view, F for full screen, ? for every shortcut. The bar along the bottom is --deck-current-slide over the slide count.

A slide is a section

<section id="intro"> <h2>Hello</h2> <p step="1">Shown on step 1</p> <aside class="notes">Say this</aside> </section>

Anything with step waits for that press.

Each slide is a section inside deck-shift. The logo flew into the corner because it has the same view-transition-name on both slides. Anything with a step attribute appears on a later press.

Steps

  • step="1" until="1" shows for step 1 only
  • step="2" waits for step 2
  • step="3" waits for step 3
Steps can do more than appear. A range shows an element for a while, then the next one waits its turn. Numbers say when.

Step state

  1. Arrive
  2. Point
  3. Leave
@container style(--deck-step-state: active) { span { color: var(--accent); } } @container style(--deck-step-state: past) { span { text-decoration: line-through; } } li { translate: calc(var(--deck-step-on) * 40px) 0; }
Every step element knows whether it is future, active or past, and its children can query that. The number --deck-step-on moves the active item along, and past items are struck through.

Code morphs too

const deck = document.querySelector("deck-shift"); deck.addEventListener("deckchange", log); deck.next();
Each line is its own syntax-highlight element. A new line appears, and lines with a view-transition-name slide into place.

Charts build too

Inline SVG, and step works on its elements. The line draws: stroke-dashoffset follows --deck-step-on. Bars grow with scale, staggered by transition-delay. Then the point: a style query on --deck-step dims the rest.

Transitions

  • fade by default
  • slide pushes the next slide in
  • none cuts

Or your own: data-transition="zoom"

:root:active-view-transition-type(zoom) ::view-transition-new(root) { animation: 0.6s ease-out both zoom-in; }
Every change is a view transition, typed by the slide it goes to. This slide zoomed in with its own type. The durations are --deck-slide-duration and --deck-step-duration.

Buttons need no script

<button command="--goto:focus.2" commandfor="deck"> Step state, step 2 </button>

data-no-advance: click and type here, the deck stays put.

Invoker commands drive the deck, including commands other components add, like --present. Buttons, links and form controls never advance the slide, and data-no-advance opts anything else out.

Script it

deck.addEventListener("deckchange", (e) => { document.documentElement.dataset.slide = e.id; }); deck.addShortcut("--blank", "b", blank, "Blank the screen");

That made the webcam big on the title slide.

Press B to blank the screen, ? to see it.

deckchange fires inside the transition, so anything it changes animates. addShortcut adds a key, a command and a help row.

Presenter view

Press S: timer, clock, the next slide, and these notes.

Each <mark> in the notes is a press.

<deck-presenter> <template> <style>::part(cue-next) { background: #ffb454; }</style> <webcam-view mirror></webcam-view> </template> </deck-presenter>
A new chapter, so this slide dipped through black. Press S now. The presenter window shows these notes and highlights the next cue, so you know when to press. A template child injects styles, scripts and elements, like the webcam in its corner.

Record the talk

  • R records camera, mic, steps, clicks and keys
  • . pauses, marking a cut
  • npx deck-replay turns it into a video
The recording is a Puppeteer Replay flow, timed against the video. The webcam outline comes from the recorder's :state(recording).
